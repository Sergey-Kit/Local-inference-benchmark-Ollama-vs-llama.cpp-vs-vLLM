# P1 — Бенчмарк локального инференса: ТЗ для Claude Code

> Проект №1 из роадмапа портфолио. Цель — поднять одну модель на трёх рантаймах
> (Ollama / llama.cpp / vLLM), честно замерить и сравнить, сделать выводы «когда что».
> Усилия: 🟢 выходные. Результат должен быть **резюме-годным**: репозиторий + цифры + графики + README.

---

## 0. Прежде чем начинать: проверка железа

Перед выбором сценария **обязательно** определить конфигурацию, от неё зависит план:

```bash
nvidia-smi                        # есть ли NVIDIA GPU и сколько VRAM
nproc && free -g                  # ядра и RAM
python -c "import torch; print(torch.cuda.is_available())"
```

### Ветка A — есть NVIDIA GPU (≥8 ГБ VRAM)
Полный сценарий: все три рантайма, модель 7–8B.

### Ветка B — GPU нет / мало VRAM (CPU-only)
vLLM на CPU работает плохо и нерепрезентативен. Тогда:
- либо взять модель поменьше (Qwen2.5-3B / Llama-3.2-3B) и всё равно прогнать все три,
  **явно оговорив в README, что vLLM на CPU — не его сценарий** (это тоже вывод);
- либо заменить третий рантайм на **llama.cpp с разными backend-настройками**
  (BLAS/OpenBLAS, разное число потоков) и честно написать в README, почему.

Выбранную ветку зафиксировать в README в разделе «Условия эксперимента».

## 1. Что именно делаем

**Одна модель, один квант, три рантайма, одинаковые промпты, одинаковые параметры сэмплинга.**

| Параметр | Значение |
|---|---|
| Модель | `Mistral-7B-Instruct` или `Llama-3.1-8B-Instruct` (одна на все рантаймы!) |
| Квантизация | Q4_K_M для GGUF-рантаймов; для vLLM — AWQ/GPTQ 4-бит **той же** модели |
| Рантаймы | Ollama, llama.cpp (`llama-server`), vLLM (`vllm serve`) |
| Сэмплинг | `temperature=0`, `top_p=1`, фиксированный `max_tokens` — одинаково везде |
| Контекст | одинаковый `n_ctx` / `max-model-len` во всех рантаймах |

> ⚠️ **Главный риск проекта — нечестное сравнение.** Разные кванты, разный контекст,
> разный batch size = бессмысленные цифры. Все различия конфигурации, которые
> устранить невозможно, должны быть явно перечислены в README (раздел «Ограничения»).

## 2. Метрики

Замеряем для каждого рантайма:

| Метрика | Что это | Как считать |
|---|---|---|
| **TTFT** | Time To First Token, мс | время от отправки запроса до первого токена в стриме |
| **TPOT** | Time Per Output Token, мс/ток | `(total_time − TTFT) / (n_output_tokens − 1)` |
| **Throughput** | ток/с | суммарно сгенерированных токенов / wall-clock, при разном числе параллельных запросов |
| **Peak VRAM / RSS** | ГБ | пик по `nvidia-smi --query-gpu=memory.used` (или RSS процесса на CPU) |
| **Cold start** | с | время от старта процесса до готовности отвечать (важно для on-prem!) |

Дополнительно, если время позволит: **P50/P95 latency** (не только среднее — среднее скрывает хвосты).

### Сценарии нагрузки
Прогнать каждый рантайм минимум в трёх режимах:
1. **Single-stream** — 1 запрос за раз (интерактивный чат, важен TTFT).
2. **Concurrency 4 / 8 / 16** — параллельные запросы (важен throughput; здесь vLLM должен выигрывать за счёт continuous batching — это ключевой вывод проекта).
3. **Длинный промпт** (~2–4k токенов) vs короткий — показать, как растёт TTFT (prefill-bound).

Каждый замер — **минимум 3 прогона**, брать медиану; перед замерами — warm-up прогон (не учитывать).

### Ключевое архитектурное решение
**Все три рантайма выставляют OpenAI-совместимый `/v1/chat/completions`** — значит,
клиент бенчмарка пишется **один раз** и не зависит от рантайма. Это и упрощает код,
и делает сравнение честным (один и тот же код измерения).

- Ollama: `ollama serve` → `http://localhost:11434/v1`
- llama.cpp: `llama-server -m model.gguf --port 8080` → `http://localhost:8080/v1`
- vLLM: `vllm serve <model> --port 8000` → `http://localhost:8000/v1`

Замер TTFT делать **на стриминге** (`stream=True`): засечь время до первого чанка с непустым `content`.
Токены считать по `usage` из ответа, а не по словам — иначе цифры будут врать.

### Порядок работ
1. Скелет репо + `configs/experiment.yaml` + набор промптов.
2. `bench/client.py` + `metrics.py` — единый измеряющий клиент со стримингом.
3. `monitor.py` — фоновый семплер VRAM/RSS (поток, опрос раз в 100–200 мс).
4. Поднять Ollama, прогнать полную матрицу, убедиться, что цифры вменяемые.
5. Поднять llama.cpp с **тем же GGUF-файлом**, повторить.
6. Поднять vLLM, повторить.
7. `analysis/plots.py` → графики; `results/summary.csv` → сводная таблица.
8. README с выводами.

> Родные бенчмарк-утилиты (`vllm bench serve`, `llama-bench`) полезны как **сверка**:
> прогнать их и убедиться, что свои цифры в том же порядке. Но основной результат —
> свой единый харнесс, потому что только он даёт сопоставимые условия.

## Подсказки по граблям

- **WSL2 + CUDA**: vLLM в WSL работает, но нужен корректно проброшенный CUDA-toolkit; проверить `nvidia-smi` внутри WSL, а не только в Windows.
- **Ollama и llama.cpp должны использовать физически один и тот же GGUF-файл**, иначе сравнение нечестное (Ollama по умолчанию тянет свой квант — проверить, какой именно, через `ollama show <model>`).
- **vLLM резервирует VRAM заранее** (`--gpu-memory-utilization`), поэтому «peak VRAM» у него меряется иначе — это надо оговорить в README, а не молча сравнивать.
- Не запускать два рантайма одновременно — они подерутся за VRAM и испортят замеры.
- Фиксировать версии (`ollama --version`, коммит llama.cpp, `vllm --version`) — через полгода цифры без версий бесполезны.
